# BSLBATT Powerline 远程固件升级交付任务计划

## 1. 文档目的

根据 Victron（Rein van der Zee）的邮件要求，完成 BSLBATT Powerline 电池远程固件升级工具在 Venus OS 集成前所需的固件、代码版本、异常测试、多模块测试和产品说明文档交付。

本文档同时记录后续工作计划和截至 2026-09-03 的实际完成状态。只有取得真实测试结果和责任人确认的任务才标记为完成；部分验证、阻塞项和未执行项均明确保留。

## 2. 最终交付目标

需要向 Victron 交付以下 5 类内容：

1. 至少两个不同版本的、可用于测试的 Powerline BMS 固件文件。
2. 通过验收的远程固件升级工具代码，以及对应的 Git 版本标签。
3. 正常升级、异常中断、错误固件和多模块场景的测试报告。
4. Venus OS 集成所需的产品兼容性和停机时间说明。
5. 一封附带两个固件文件，并汇总代码版本、文件校验值和测试结论的英文回复邮件。

仓库中已有一份 1.23 升级到 1.24 的历史终端记录，但该版本低于当前确认的最低远程升级版本 `V1.245`，只能作为开发阶段参考，不能代替本计划要求的正式测试报告。

当前发布前必须处理的风险：

- 两个正式测试固件已完成单模块真实设备往返刷写验证，但目标硬件版本、发布日期和发布说明仍未由固件负责人确认。
- 尚未创建用于 Venus OS 构建的版本标签。
- 当前工具只接受节点 `0x0`，设备发现也只把一条 CAN 总线识别为一个逻辑设备；多模块行为尚未正式确认。
- 已要求裸固件文件名和 zip 包内固件成员名以大写 `BSL` 开头，但仍未校验固件头、目标型号、版本、载荷长度、固件 CRC 或数字签名。
- 当前计算的 CRC32 只用于日志，不用于判定固件是否损坏。
- `locate_device()`、`erase_flash()` 和 `verify_firmware()` 目前是占位步骤，升级成功后没有主动读取并核实设备的新版本。
- README 已使用 Product ID `0xB021`，但其中部分版本输出示例仍为旧的 `1.245`/`1.23`/`1.24` 格式，需要与当前设备输出的 `12.45`/`12.46` 规则统一并区分历史记录。
- 已完成一次约 52% 进度处的 CAN 中断测试，但 START、10%、90%、FINISH 和升级后验证阶段的中断场景尚未覆盖。
- 错误固件实测曾导致 BMS 死机，并需要通过 485 工具恢复；当前文件名前缀检查只能降低误刷风险，不能证明固件内容兼容。
- 多模块测试因模块机制未定义且无可独立识别的多模块台架而阻塞。
- 单模块正式固件实测低于 400 秒，但保守上限约为 385.714 秒，仅剩约 14.286 秒余量；工具仍没有独立的 400 秒全流程超时控制，最大模块配置和高总线负载尚未验证。

退出码验收基线：

| 退出码 | 含义 | 主要验证场景 |
|---:|---|---|
| 0 | 成功 | 正常升级；列表扫描不到设备 |
| 1 | 通用错误 | 未归类的内部错误 |
| 2 | CAN 初始化错误 | CAN 接口不存在或无法打开 |
| 3 | CAN 通信错误 | CAN 发送/接收发生系统级错误 |
| 4 | 超时 | 设备未返回 START/DATA/FINISH ACK |
| 5 | 固件错误或不兼容 | 错误型号、版本路径不支持或格式不兼容 |
| 6 | 参数错误 | CAN 接口、节点或文件参数错误 |
| 7 | 未找到设备 | 升级目标无法定位 |
| 8 | 设备存储器/升级异常 | BMS 返回升级错误帧 |
| 9 | 文件错误 | 文件缺失、损坏或 CRC/签名失败 |
| 10 | 升级验证失败 | 升级后版本或设备校验结果不正确 |
| 11 | 升级验证超时 | 升级后设备未在规定时间恢复并报告版本 |

说明：固件“损坏”和“不兼容”最终分别映射到退出码 9 或 5，必须结合 Victron 约定和最终实现固定下来，并在文档中保持一致。

### 4.5 CAN 中断和故障恢复测试

责任方：测试人员、BMS 固件团队

分别在下列阶段断开 CAN 线：

- [x] 固件写入约 50% 时。实测最后有效 ACK 为 52%，工具返回码 4；BMS 重启后恢复原版本。

本轮 CAN 中断测试以约 52% 断点为最终范围，不再补充 START、10%、90%、FINISH 或升级后验证阶段的断线测试。未覆盖阶段不得在对外报告中描述为已验证。

每个场景均需检查：

- 工具是否在可接受时间内退出。
- 返回码是否为预期的 CAN 通信错误、超时或验证错误，且绝不能返回 0。
- VRM 可见消息是否准确。
- BMS 是否仍处于安全状态。
- 重新连接 CAN 后是否能恢复应用程序或重新进入升级流程。
- 是否能够再次使用正确固件完成升级。
- 是否需要断电重启或人工恢复；如需要，必须写入用户文档。

建议的预期结果：

- CAN 接口仍存在但收不到 ACK：退出码 4。
- CAN 接口被关闭或发送/接收发生系统错误：退出码 3。
- 固件已经写入但设备未能重新上线或版本不正确：退出码 10 或 11。

最终预期返回码以实测和协议确认结果为准，并写入测试报告。

当前实现每帧传输 7 字节，帧间隔为 20 ms，并且每 10 帧等待一次 ACK。仅按固定帧间隔估算，传输 100 KiB 固件约需 293 秒，尚未包含 ACK、启动、结束、系统调度和总线竞争时间。本轮以单模块真实硬件结果作为结论依据。

单模块专项测试结论：用例 09 的 CAN 协议耗时为 373.688 秒，从提前设置的 shell 开始标记到 `FINISH_ACK` 的保守上限约为 385.714 秒，因此单模块正常负载场景通过 400 秒限制。该结果不代表最大模块数量或高总线负载场景通过，且距离 400 秒仅约 14.286 秒的保守余量。

验收标准：

- 本轮单模块正常负载场景实测时间小于 400 秒。
- 测试报告明确说明该耗时结论只适用于单模块正常负载，并注明多模块关系未实测。
